# こころの荷物置き場 セキュリティ仕様書 v1

- 版: v1.0
- 制定日: 2026-10-27
- 対象: 検索需要実証サイト、および将来のAI文章・音声会話機能
- 基本原則: **収集しない / 保存しない / 結び付けない / 最小権限 / 侵害を前提に被害を小さくする**

## 1. 守る対象

### C0 公開情報
公開ページ、説明文、SEOコンテンツ。機密性は低い。

### C1 利用統計
ページパス、会話前の希望選択、入力開始、文章AI・音声AIへの関心、評価値。自由記述本文を含めない。

### C2 高機密データ
会話本文、音声、文字起こし、任意提供された改善用会話。氏名がなくても健康、家族、勤務先、人間関係等から本人を推測できる可能性があるため、常に個人情報を含み得るデータとして扱う。

### C3 認証・秘密情報
AI APIキー、DB資格情報、管理者セッション、暗号鍵、デプロイトークン。ブラウザへ配布しない。

## 2. 現行テスト版の必須要件

- GitHub Pagesの静的サイトとして稼働し、PHP等のサーバーランタイムを置かない。
- 自由記述本文をサーバーへ送信・保存しない。
- GA4へ自由記述本文、メールアドレス、電話番号等をイベントパラメータとして送らない。
- GA4へ送る値は列挙済みのイベント名・選択肢・ページパスに限定する。
- 改善用本文の送信エンドポイントはソース上で固定無効とする。ブラウザのグローバル変数から任意URLを設定できる設計は禁止する。
- 入力欄は autocomplete / autocorrect / spellcheck を無効化する。
- ページ離脱時に本文を消去し、BFCache復帰時にも本文を復元しない。
- CSPでスクリプト・通信先を自サイトと必要なGA4関連ドメインに限定する。
- Referrer-Policyは strict-origin-when-cross-origin とする。
- ユーザー入力を innerHTML として描画しない。将来AI出力をHTML表示する場合もサニタイズなしのHTML挿入を禁止する。
- APIキー、DBパスワード、秘密鍵をGitリポジトリへコミットしない。

## 3. 将来AI会話を有効化する際のアーキテクチャ

必須経路:

Browser -> 自前API -> AI事業者

禁止:

- Browser -> AI事業者APIへ秘密鍵付きで直接通信
- Browser -> DBへ管理者権限で直接通信
- 公開JavaScript内へのAPIキー埋め込み

自前APIは以下を満たすこと。

- HTTPSのみ。
- 許可Originを本番ドメインへ限定する。ワイルドカードCORSは禁止。
- POSTのJSONのみ受け付け、スキーマ検証を行う。
- リクエスト本文サイズ上限を設ける。
- IP/匿名セッション単位でレート制限する。
- タイムアウト、同時実行数上限、AI利用額上限を設定する。
- URL・クエリ文字列へ会話本文を入れない。
- エラーレスポンスへ内部スタック、秘密情報、DB情報を返さない。
- AIツール実行機能を追加する場合、ユーザー本文だけを根拠に任意の外部操作やコード実行を許可しない。

## 4. 会話本文の保存

### 通常会話
原則保存しない。AI応答生成に必要な時間だけメモリ上で処理し、永続DBへ書き込まない。

### 改善用の任意提供
会話終了後にユーザーが明示的に「匿名で提供する」を選んだ場合のみ保存可能。

保存時の条件:

- 「匿名」は完全な匿名性を保証する表現として扱わず、個人情報を含み得るデータとして管理する。
- 利用統計のユーザー識別子、IP、広告識別子等と本文を直接結び付けない。
- IPアドレスを本文レコードへ保存しない。
- 原文の保持期間は原則30日以内とし、自動削除する。
- バックアップにも同等の削除方針を適用する。
- 長期保存が必要な分析結果は、本文を破棄した集計値・分類値を優先する。
- 自動マスキングを行っても漏れがあり得るため、マスキング済み本文も高機密として扱う。

## 5. ログ

アプリケーションログ、アクセスログ、エラートラッキングへ以下を記録しない。

- 会話本文・音声・文字起こし
- パスワード
- APIキー・アクセストークン
- DB接続文字列
- セッションIDの生値
- 健康情報等のセンシティブ情報

必要な監査ログは、管理者ログイン、設定変更、データ閲覧、削除、エクスポート、権限変更等の「操作事実」を記録し、本文を記録しない。

## 6. 管理画面

- 一般ユーザー向けアプリと管理機能を論理的に分離する。
- 管理者認証はMFAを必須とする。可能ならパスキーを優先する。
- 管理者数を最小化する。
- 最小権限RBACを採用する。
- 本文閲覧権限とシステム管理権限を分離できる設計を優先する。
- 管理者操作を監査ログへ残す。
- 共有アカウントは禁止する。

## 7. DB / ストレージ

- Public bucketに会話本文・音声を置かない。
- Row Level Security等、利用するDBのアクセス制御機構を必須とする。
- サーバー管理キーをクライアントへ配布しない。
- 保存時暗号化を有効化する。
- C2データを長期保存する場合、アプリケーション層暗号化と鍵の分離管理を検討する。
- 本番・検証・開発環境のデータを分離する。本番本文を開発環境へコピーしない。

## 8. XSS / コンテンツ安全性

- ユーザー入力は textContent / value として扱い、innerHTMLへ直接入れない。
- Markdownを導入する場合は許可タグ方式でサニタイズする。
- javascript: URL、イベントハンドラ属性、iframe等を許可しない。
- CSPは本番ホスティングでHTTPレスポンスヘッダーとして設定する。GitHub Pages検証版のmeta CSPは暫定措置。
- 本番では frame-ancestors、HSTS、X-Content-Type-Options、Permissions-Policy 等をHTTPヘッダーで設定する。

## 9. 音声機能

- マイク権限はユーザー操作時だけ要求する。
- 常時録音しない。
- 音声ファイルは原則保存せず、必要な場合も一時保存後に削除する。
- 音声URLを公開URLにしない。
- 文字起こしもC2として本文と同じ保護を適用する。

## 10. 秘密情報と依存関係

- Secrets Manager / ホスティング環境のSecret機能を使う。
- .env を公開Gitへコミットしない。
- 依存パッケージを導入した場合はlockfileをコミットし、脆弱性通知を有効化する。
- PHPを導入する必然性がない限り、本プロジェクトではPHPを採用しない。
- Critical脆弱性: 原則24時間以内に緩和または修正版へ更新。
- High: 原則72時間以内。
- 侵害・漏えいの疑いがある場合は期限を待たず、該当機能停止・鍵失効を優先する。

## 11. インシデント対応

1. 影響機能を停止または隔離する。
2. APIキー、トークン、管理者セッションを失効・ローテーションする。
3. 本文を含まない監査ログから影響範囲を確認する。
4. 漏えい対象、件数、期間、第三者提供先の可能性を整理する。
5. 法令・個人情報保護委員会の基準に従い、報告・本人通知の要否を判断する。
6. 修正後に再発防止策を実装し、原因と対策を記録する。

## 12. リリースゲート

AI会話、保存、音声のいずれかを本番有効化する前に、以下が全てYESであること。

- [ ] APIキーがクライアントに存在しない
- [ ] 会話本文がGA4/ログ/URLへ流れない
- [ ] DBのアクセス制御を第三者ユーザー視点でテストした
- [ ] CORSが本番Origin限定
- [ ] レート制限・利用額上限がある
- [ ] 管理者MFAが有効
- [ ] 保存期間と自動削除が実装済み
- [ ] バックアップ削除方針がある
- [ ] CSP等の本番HTTPセキュリティヘッダーを確認した
- [ ] XSSテストを実施した
- [ ] エラーログに本文が残らないことを確認した
- [ ] プライバシー表示を実装内容に合わせて更新した
- [ ] インシデント時に即時停止できる手順がある
